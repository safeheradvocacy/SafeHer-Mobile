# Unresolved evidence and testing register

This is the single consolidated list the governing master prompt asked for:
"which previous findings require runtime testing or additional evidence."
Every row below traces back to a specific section of
`01-deliverable-1-project-structure.md`, `02-deliverable-2-feature-matrix.md`,
or `03-prior-documentation-reconciliation.md` — nothing here is a new claim;
this document only re-sorts and prioritizes what those three already
identified, so the team has one place to work from instead of ten
"Additional testing required" rows scattered across files.

Priority is about **manuscript risk and system risk**, not difficulty:
**Critical** items are things the manuscript cannot honestly claim are
secure/working without evidence, or things that would be genuinely harmful
if wrong in production. **High** items materially affect specific feature
claims. **Medium/Low** items are real but narrower or cosmetic.

## High

| # | Item | Why it matters | What would resolve it | Source |
|---|---|---|---|---|
| H1 | Case status transitions (`CASE_STATUS_FLOW`) are enforced only in the admin UI's TypeScript, with **no** corresponding database trigger/CHECK constraint — unlike the comparable transition guards that do exist for `expert_support_requests`, `sos_alerts`, and `barangay_action_requests`. | A direct API call bypassing the admin UI could set a case to any status in any order, limited only by RLS ownership, not sequence. | Confirm via a direct (non-UI) API write whether an invalid sequence is actually accepted; if so, decide whether a DB-level guard is worth adding. | `02-*.md` §5 |
| H2 | Several write paths silently report success to the admin even when the underlying Supabase write fails: `submitStatusChange`/`submitAssignment` in `CaseDetailPage.tsx` (no error check at all), and `updateRequestStatus`/`updateReferralStatus`/`bumpOccupancy` in the shared shelter hook (`useShelterAdminData.ts`, shows a success toast regardless of the `{ error }` result). | A staff user could believe a case was reassigned or a shelter placement confirmed when it was not, with no indication anything went wrong. | Reproduce with a deliberate failure (e.g., revoke the relevant RLS grant temporarily on a test account, or simulate a network drop) and observe what the UI actually shows. | `02-*.md` §5, §6 |
| H3 | Shelter `current_occupancy` is a fully manual integer with no DB-level consistency mechanism and no "discharge" workflow to decrement it — it can only drift further from reality over time, and a race condition is plausible since the increment is a read-then-write with no row lock found. | Shelter capacity is operationally important (it is how a referral/request decision gets made) and currently has zero integrity guarantee. | A concurrency test (two simultaneous acceptances) and a decision on whether a "discharge" workflow or an atomic increment/trigger is worth adding. | `02-*.md` §6 |
| H4 | Push notifications cannot currently reach a real device end-to-end — no EAS project is configured, per the client code's own header comment — so the entire remote-push half of the notification pipeline is implemented but unproven. | A manuscript claim of "push notifications" working needs this prerequisite resolved first; testing anything about push delivery before this is pointless. | Configure an EAS project, then run one real end-to-end test (register a token on a real device, trigger a high-priority notification, confirm receipt). | `02-*.md` §9 |
| H5 | `admin/src/lib/permissions.ts` (the UI-layer permission map) and the actual RLS policies have never been systematically checked for drift across all 8 roles — the file itself documents that it is "a UI-layer convenience, not the actual security boundary," but whether it and RLS agree in every case is unverified. | A drift in either direction is either a confusing-but-safe UX issue or, more seriously, a UI element that looks available but is silently rejected — neither has been checked. | A role-by-role, page-by-page comparison of what `permissions.ts` allows vs. what the corresponding RLS policy allows. | `02-*.md` §2 |
| H6 | `logAudit()` coverage across the codebase (31 known call sites across 17 files, cataloged this pass) has **not** been exhaustively checked against every mutating action in the codebase — audit completeness is "substantial" by observation, not "complete" by verification. | The audit log's own UI already discloses it is not tamper-evident; if it is also incomplete, that compounds the limitation and the manuscript should state both precisely rather than either one being assumed away. | A full, mechanical pass cross-referencing every `supabase.from(...).insert/update/delete(...)` call site in `admin/src` against the 31 known `logAudit()` call sites, to find any mutation with no corresponding audit entry. | `02-*.md` §10 |
| H7 | No jurisdiction/station/precinct restriction exists anywhere in the law-enforcement access model — any active officer can see any SOS alert province-wide. This is a documented, deliberate design choice (module19's own header), not an oversight, but it has never been evaluated as a policy decision by the team outside the code comment that justifies it. | This is exactly the kind of tradeoff a capstone panel is likely to ask about directly — "why can an officer in one town see an alert from another?" — and the answer should come from the team's own judgment, informed by this finding, not be discovered live during a defense. | A team discussion/decision, documented, on whether this tradeoff is acceptable for the final manuscript, independent of any code change. | `02-*.md` §7 |

## How to use this register going forward

- When an item is resolved, **mark it resolved in place** (e.g., prefix the
  row's first cell with "**RESOLVED (2026-XX-XX):**" and a one-line pointer
  to the evidence) rather than deleting the row — this preserves the audit
  trail of what was checked and when, consistent with the evidence-tagging
  discipline used throughout this audit.
- New items discovered in a future pass should be added with the same
  five-column shape and slotted into the appropriate priority tier, not
  appended to the bottom regardless of severity.
- This register does not replace the "Additional testing required" row in
  each Deliverable 2 feature table — it exists so the team has one
  prioritized view across all of them, not so the per-feature detail can be
  deleted.
