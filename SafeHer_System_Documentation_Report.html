01

Background & Problem

Why a case that starts at a barangay desk needs to survive contact with every tier above it.

Response to Violence Against Women and Children (VAWC) in a province like Aurora runs through a real administrative chain: a barangay intake, escalation to the Municipal Social Welfare and Development Office, and where needed, coordination with the Provincial Social Welfare and Development Office (PSWDO), shelters, and law enforcement. Each of Aurora's eight municipalities — Baler, Casiguran, Dilasag, Dinalungan, Dingalan, Dipaculao, Maria Aurora, and San Luis — runs its own intake point, and a report that needs to move from one tier to the next has historically depended on that information travelling by phone, paper, or in person without getting lost, delayed, or seen by someone who shouldn't see it.

That model has three structural weaknesses, independent of how carefully any individual office runs:

  1. Fragmented, non-real-time reporting. A report's status lives wherever its paper or spreadsheet currently sits. Neither the survivor nor the next tier can see it move — someone has to remember to forward it.
  2. No unified emergency channel. A survivor in immediate danger has no direct, location-aware way to summon a responder; the fallback is a phone call chain that depends on someone being reachable and able to describe where they are.
  3. Confidentiality is procedural, not structural. A shared spreadsheet or paper folder has no per-role boundary — what a barangay clerk, a shelter intake worker, or a referred officer can see is governed by discipline and trust, not by a system that enforces it.

SafeHer was built to replace that chain with one governed system of record: a survivor-facing mobile app and a multi-role administrative web app, sharing a single Postgres database and a single authorization model, so that a report, an SOS alert, or a referral is the same row from the moment it is created through every tier that legitimately needs to act on it — and is structurally, not procedurally, invisible to every tier that does not.

02

Objectives

General objective, then the seven specific objectives each implemented module maps back to.

General objective — design and implement a confidential, role-differentiated digital platform that lets VAWC survivors in Aurora Province report incidents, request emergency assistance, and track their case, while giving barangay, municipal, and provincial responders — plus shelter staff, law enforcement, and support specialists — a coordinated, access-controlled system of record for that same case.

Specific objectives

  1. Confidential reporting. Give survivors a mobile channel to report an incident — with optional anonymity — attach evidence, and track case status without re-contacting an office.
  2. Real-time emergency alerting. Provide an SOS channel, distinct from routine reporting, that carries live location to the correct tier of responder immediately.
  3. Enforced, jurisdiction-scoped access. Implement the barangay → municipal → provincial hierarchy, plus shelter, law-enforcement, and support-specialist roles, as database-level authorization — not an interface convention that a direct API call could bypass.
  4. Shelter coordination. Support both survivor-initiated shelter requests and admin-initiated referrals against real, live capacity data.
  5. Identity verification & walk-in access. Support ID-document verification and a QR-based case-access path for survivors who report in person or without an account yet.
  6. AI-assisted first response. Offer guided, safety-boundaried AI assistance with an explicit, auditable handoff to a human support specialist.
  7. Auditable administrative oversight. Give administrators activity logs, administrative-data backups, and case-management reporting, scoped to what each role is authorized to see.
03

Methodology

A schema-first, security-first, iteratively verified build — not a single upfront design frozen at day one.

Architecture

Two client applications share one backend and one canonical type definition, so the mobile app and the admin dashboard can never silently disagree about a column name, an enum value, or a status transition.

Build discipline

The backend was built as one baseline schema (00_schema.sql) followed by 17 sequential, additive modules — each introducing one role, one capability, or one fix, with row-level security written alongside the table it protects rather than retrofitted. Four of the eighteen files exist specifically because a live test surfaced a real gap after the fact rather than being planned upfront — module 1b (missing PostgREST grants), 3b (the service role had no table grants, silently breaking admin provisioning), 15 (the public registration dropdown was broken for every municipality because barangays had never been granted to anon), and 17 (the law-enforcement referral fix described in §5–6). That pattern — build, verify against a real client, patch what the verification found — is the actual methodology, not a single upfront design frozen on day one.

Two conventions recur across the whole schema:

  • Two-part migrations for enum changes. Postgres will not let a newly added enum value be referenced inside the same transaction that added it, so every module that introduces a new role or status value ships as Part A (add the value) / Part B (everything that uses it), run as two separate statements.
  • Live verification block in every module. Each module file ends with a commented-out set of read-only queries — confirm the policy count, attempt a denied read as an unauthorized role, check for the recursion error Postgres raises if a policy cycle is accidentally introduced — meant to be run against the real project immediately after applying the migration, not taken on faith.

Security model

Authorization is enforced by Postgres row-level security (RLS), scoped to the actual relationship the schema already models — municipality/barangay jurisdiction for the geographic tiers, direct assignment for shelter staff and law enforcement, shelter membership for shelter roles — never a fabricated hierarchy invented to make a feature easier to build. Where a policy needs to check a related table without triggering a recursive-policy error, a narrow SECURITY DEFINER helper function with row_security = off is used, scoped to answer exactly one yes/no question rather than opening a general bypass.

Admin app — 9 roles, one codebase

Rather than separate deployed apps per role, SafeHer is one React application with role-gated routing, navigation, and data queries — the same login screen and components for every role, with the sidebar and every query scoping themselves to profile.role. This avoids duplicating the ~70% of code every role shares, while jurisdiction and permission are still fully separated at the data layer.

Backend capabilities (Postgres · Auth · Storage · Realtime · 5 Edge Functions)

  • Row-level security everywhere. Every table a client can reach is governed by policy, scoped to the real jurisdiction/assignment relationship — never using (true) on a sensitive table.
  • Hybrid notification pipeline. A database-row-first notification, checked for priority, then dispatched as an Expo push notification via an internal Edge Function call — never the reverse.
  • Identity verification queue. Barangay/municipal review of submitted ID documents, gating incident-report submission.
  • Walk-in & QR case access. Cases created with no account yet, an opaque hashed QR bearer token (never the raw token stored), and an admin-verified authorization link to a survivor's account after the fact.
  • Administrative-data backup. Scheduled (pg_cron) and on-demand export of municipalities/barangays/shelters — explicitly not a substitute for full database point-in-time recovery (see §7).
  • AI assistant with a hard safety boundary. Rule-based safety check → FAQ match → guided intent → LLM fallback, with the LLM never the first responder to a safety-flagged message.

Testing & Evaluation

Three layers of verification, applied the same way to every module: static checks, then live security checks against the real project, then a scenario walk-through.

Static verification

Both apps type-check clean (tsc --noEmit) and the admin app additionally builds clean (vite build) before any module is considered done — not run once at the end, but re-run after every schema or frontend change in this build.

Live security verification

Because row-level security is the actual authorization boundary, it is tested the same way an attacker or a misconfigured client would exercise it: disposable test accounts, real REST calls carrying a real signed-in JWT for each role, run directly against the project — never assumed correct from reading the policy text alone. Scope of evaluation

This verification method — live RLS checks under a real JWT per role, run against the actual project rather than inferred from policy text — is the same discipline every one of the 18 backend modules documents in its own end-of-file verification block: confirm the policy count, attempt a denied read as the wrong role, and check for the specific Postgres error a recursive policy would raise. It is thorough for what it covers, but it is manual and scenario-driven rather than an automated regression suite — see the recommendation in §7.

07

Conclusion & Recommendations

What the system achieves, and where its own documentation already flags the honest limits.

SafeHer replaces a paper-and-phone-call coordination chain with one governed system of record spanning eight municipalities and nine distinct responder roles. Reporting, SOS emergency alerting, shelter coordination, identity verification, and law-enforcement referral all run through the same row-level-security model rather than nine independent access conventions — the property that made the §5–6 fix possible to verify with confidence rather than guesswork: the policy was provably correct, and the gap was provably a missing interface action, not a security hole.

Recommendations

  1. Enable full database point-in-time recovery. The current backup module intentionally covers administrative reference data only (municipalities, barangays, shelters) and documents, explicitly, that Supabase PITR is not yet enabled on the project. Case, SOS, and verification data currently have no equivalent disaster-recovery path.
  2. Move live RLS verification into an automated suite. The scenario-based, disposable-account method in §6 is sound but manual. Converting the recurring scenarios (unassigned-record denial, cross-role denial, unauthenticated denial) into a scripted regression suite would let every future module reuse them instead of re-deriving the checks by hand.
  3. Revisit the law-enforcement access model if the province formalizes a police organizational unit. Access is currently per-referral assignment rather than by precinct or unit, a deliberate choice made because no such organizational concept exists yet in the schema or the province's own structure. If one is formalized, the referral model — not the RLS pattern — is what should be extended.
  4. Plan an offline/SMS fallback for low-connectivity areas. SOS and reporting currently assume a data connection; this was scoped out deliberately rather than overlooked, and is worth a dedicated feasibility pass given Aurora's geography.
  5. Keep the single-admin-app decision, but watch its bundle size. One role-gated app avoids duplicating shared code across nine roles; the production build already warns on chunk size, which is worth addressing with route-level code-splitting before it affects load time on slower connections.
