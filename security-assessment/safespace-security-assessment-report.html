1Introduction and System Description

SafeSpace is a mobile and web-based abuse reporting and response system built for Aurora Province, Philippines. It handles some of the most sensitive data a civic system can hold: survivor identities, abuse incident reports, uploaded evidence, emergency SOS alerts with live location, shelter placements, police referrals, and confidential survivor-to-counsellor conversations.

That data sensitivity is what makes this assessment's scope decisions matter. A vulnerability that would be a minor nuisance in a retail application can, in this system, expose the identity and physical location of a person fleeing violence. The assessment was therefore weighted toward confidentiality and authorization rather than availability.

Architecture

SafeSpace consists of three deployed components and one managed backend:

ComponentTechnologyDeployment
Mobile applicationReact Native, Expo SDK 57, HermesAndroid, package ph.pswdo.safeher, distributed via Expo EAS
Administrative dashboardReact 18, Vite 5, React Router 6Vercel — safespace-administrative.vercel.app
Backend & databaseSupabase, PostgreSQL 15Project qhhcqehgwpzeycejgevk
Server-side logicDeno Edge Functions × 7Supabase Edge runtime

Authentication uses Supabase Auth with email confirmation, password reset, and refresh-token session management. Authorization is enforced in two layers: PostgreSQL table grants, which decide whether a database role may touch a table at all, and Row Level Security policies, which decide which rows within that table it may see. The database schema is defined across 41 sequential SQL migration files establishing 35 tables and 96 RLS policies.

A ninth role model governs access: survivor, barangay_admin, municipal_admin, provincial_staff, provincial_admin, super_admin, shelter_admin, support_expert, and law_enforcement. Each is scoped by jurisdiction, assignment, or both.

2.3 Validation discipline

Two test runs during this assessment produced plausible but invalid output, and both were discarded rather than reported. They are documented here because the discipline matters more than the clean result:

  1. An Edge Function authentication test extracted a zero-length API key, so one of its four test columns silently tested an empty string. Re-run with a valid key.
  2. An unauthenticated REST probe used a key extracted from the APK's Hermes bytecode. Hermes concatenates adjacent strings in its string table, so the regular expression captured 60 characters instead of 46. Every one of the 35 tables returned a uniform 401 Invalid API key. Reported as-is, this would have read as “all tables correctly deny unauthenticated access” — a false conclusion that would have concealed a real exposure. Re-run with the valid 46-character key from the web bundle.
  3. An initial reading of the Android manifest by string extraction reported android.permission.DUMP and BIND_JOB_SERVICE among the permissions the application requests. Decoding the binary manifest properly showed both are permission guards restricting who may invoke two internal receivers and one service — close to the opposite meaning. The error is described in §3.4 and the finding was corrected. Extracting strings from a binary format recovers the values but discards the structure that gives them meaning.
Principle

A uniform result across every target is a signal to verify the test apparatus, not to record a pass. Scanner and script output is a hypothesis until its validity is confirmed — including, as the third case above shows, output produced by the assessor's own tooling.

3.1 Database authorization — verified live

Static review identified RLS enablement statements for all 35 table definitions across the 41 migration files. This was then confirmed against the deployed database. A read-only pg_class query returned rls_enabled = true for all 35 tables, and the deployed table set matched the repository migrations exactly, with no drift in either direction.

Deployed schema vs. repository migrations2026-10-21
deployed tables: 35   repo tables: 35
=== in REPO but NOT deployed ===
=== DEPLOYED but not in repo migrations ===
=== (empty sections above = exact match) ===

Unauthenticated probing of all 35 tables through the live PostgREST API established where the perimeter actually sits. Thirty-three tables were denied, and critically, the denial occurs at the PostgreSQL grant layer — error 42501 — before any RLS policy is evaluated:

GET /rest/v1/case_reports — anon key, no user sessionHTTP 401
{"code":"42501",
 "message":"permission denied for table case_reports",
 "hint":"Grant the required privileges to the current role with:
         GRANT SELECT ON public.case_reports TO anon;"}

This is meaningful defense in depth: the anon role holds no table privilege whatsoever on sensitive tables, so an RLS policy misconfiguration alone could not expose them to an unauthenticated caller. Two tables did return data — municipalities (8 rows) and barangays (151 rows) — containing Philippine Standard Geographic Codes, place names, and public government office numbers. These are required by the registration flow to populate address selectors before an account exists, and the exposure is appropriate.

Policy structure analysis of all 96 deployed policies surfaced two properties worth recording. First, only three tables carry any DELETE policy. case_reports, evidence, sos_alerts, chat_messages, survivors, and audit_logs have none, meaning no client role can delete those records under any circumstance — a strong integrity property for an abuse-reporting system. Second, audit_logs permits INSERT and SELECT but neither UPDATE nor DELETE, making it append-only at the policy layer.

Three tables — security_passcodes, protected_access_grants, and profile_photo_changes — have RLS enabled with zero policies. This was investigated rather than assumed to be an oversight, and proved deliberate: module37_profile_photo_limits.sql line 99 contains an explicit revoke all on public.profile_photo_changes from authenticated, anon;, and the other two are reachable only by the security-passcode Edge Function through the service role. Zero policies means deny-all for every client role — correct fail-closed design.

3.3 Transport and deployment configuration

TLS configuration passed. TLS 1.0 and 1.1 are rejected; 1.2 and 1.3 are supported; connections negotiate TLS 1.3 with TLS_AES_128_GCM_SHA256. The certificate is issued by Google Trust Services, valid 29 August to 27 November 2026, and chain verification returns 0 (ok). The certificate is Vercel's shared *.vercel.app wildcard, so renewal and key management are entirely provider-controlled — acceptable, but worth noting as an external dependency.

Security headers were inspected live. HSTS is present with a two-year max-age, includeSubDomains, and preload. Five headers are absent, giving finding F-09:

Response headers — safespace-administrative.vercel.appHTTP 200
Strict-Transport-Security : max-age=63072000; includeSubDomains; preload   PRESENT
Content-Security-Policy   : ABSENT
X-Frame-Options           : ABSENT
X-Content-Type-Options    : ABSENT
Referrer-Policy           : ABSENT
Permissions-Policy        : ABSENT
Access-Control-Allow-Origin: *   (on the static HTML document)

The absence of both X-Frame-Options and a CSP frame-ancestors directive means the administrative dashboard can be embedded in an iframe by any origin, enabling clickjacking against an authenticated administrator. For a dashboard that manages survivor case records, SOS dispatch, and shelter placement, this is the most consequential issue identified. Source maps were confirmed not exposed (HTTP 403 on the .map path).

A sweep for commonly leaked deployment files (.env, .git/config, package.json, .vercel/project.json and six others) returned HTTP 200 for every path — which looks alarming and is not. Each response carried content-type: text/html at exactly 674 bytes, identical to the application shell, because vercel.json rewrites all unmatched routes to index.html. No file is exposed. Reporting the status codes alone would have produced ten fabricated Critical findings; the content type and response size are what distinguish a served file from a catch-all rewrite (F-20).

This resolves several properties that would otherwise have remained unverified. allowBackup is confirmed false in the shipped artifact, so the application's private storage — including its session token — cannot be extracted through an ADB backup. targetSdkVersion 36 means cleartext HTTP is blocked by the framework default, which is why the absence of a custom network security configuration is correct rather than an omission. Of five exported components, four are permission-guarded; the single unguarded one is MainActivity, which must be exported to appear in the launcher. The embedded-credential scan passed. The Hermes bundle contains the Supabase project URL and the public publishable key — both public by design — and no service-role key, legacy JWT, or AI provider credential. The Groq key used by the AI support assistant correctly resides server-side in the Edge Function.

Two warrant scrutiny: RECORD_AUDIO (microphone, with no corresponding SafeSpace feature) and SYSTEM_ALERT_WINDOW (draw over other applications). The threat model makes this more than a hygiene issue. The sixteen launcher-badge permissions are noise from a badge library rather than a security concern, but they inflate the permission list a cautious user sees at install time.

Correction to an earlier reading

An initial analysis of this finding, produced by extracting strings from the binary manifest, listed android.permission.DUMP and BIND_JOB_SERVICE among the permissions the application requests. Decoding the manifest structure showed that both appear as android:permission guards on two internal receivers and one service — restrictions on who may invoke those components, not capabilities the application acquires. The claim was withdrawn. It is recorded here rather than silently removed, because the failure mode generalises: extracting strings from a binary format recovers values while discarding the structure that determines what they mean.

Finding F-14: the Google Maps API key is embedded in the manifest, which is unavoidable for the native Maps SDK — the control is key restriction in Google Cloud Console, not secrecy. Testing the key returned REQUEST_DENIED, but because billing is disabled on the Cloud project, not because of an application restriction. Whether a package-and-signature restriction exists therefore remains undetermined, and the risk is latent: enabling billing without first configuring restrictions would make this trivially extractable key immediately abusable. The same result also indicates that Maps functionality may be non-operational in production, which requires separate functional verification.

4Analytics, Charts, and Interpretation

Both charts below are generated from the twenty recorded findings. Passing controls are counted separately from issues throughout, since a verified control is evidence of a working defence, not a vulnerability.

Interpretation

The severity distribution should be read alongside the coverage limits in section 5.3. Zero Critical and zero High findings is a genuine result for the tests performed, and it is not a claim that none exist. The tests that would most plausibly surface a High or Critical finding in this system — one survivor reading another's case, an administrator crossing a jurisdictional boundary, a support expert reaching an unassigned conversation — are exactly the tests that were not performed.

What the category distribution does show is where attention is unevenly distributed. The backend authorization model is layered and was built carefully: grants and RLS are independent, the service-role key never leaves the server, Edge Functions validate tokens rather than trusting headers, and three tables are deliberately locked to deny-all. By contrast, deployment configuration — HTTP response headers, Google Cloud key restrictions, the permission set in the shipped artifact — shows the pattern of being accepted at framework defaults rather than deliberately configured. Every Medium finding in this assessment falls in that second group.

7F-10Construct caller-scoped Edge Function clients from the anon key rather than the service-role key, so the failure mode of a lost header override is no access rather than full database access.Low

5.2 Recommended follow-up testing

The highest-value remaining work is authenticated role-boundary testing. A test harness was written for this purpose during the assessment but was deliberately not executed, because the only available environment was production and the test records it requires could not be removed afterwards by any client role — a direct consequence of the (correct) absence of DELETE policies on case_reports. The recommended sequence is:

  1. Provision a staging Supabase project from the same 41 migrations.
  2. Create disposable accounts for each of the nine roles.
  3. Execute cross-tenant probes: can survivor A retrieve survivor B's case by direct row ID; can a barangay administrator read another barangay's records; can a support expert reach an unassigned conversation.
  4. Attempt privilege escalation by self-modifying user_profiles.role.
  5. Run OWASP ZAP for a full passive baseline, and MobSF for dynamic mobile analysis, neither of which this assessment could execute.
  6. Capture the Google Cloud Console restriction configuration for the Maps key, which resolves F-14 either way.

5.3 Limitations

This assessment is scoped, not exhaustive. The following are stated so that no reader mistakes its conclusions for broader assurance:

  • No authenticated testing was performed. Every authorization result describes the unauthenticated perimeter. Role-to-role data isolation is unverified.
  • RLS policy correctness is unverified. It is confirmed that RLS is enabled on all 35 tables and that 96 policies exist. Whether each policy's USING and WITH CHECK expressions are correct was not tested at runtime.
  • OWASP ZAP, MobSF, and Semgrep were not run, for the environment reasons in section 2.2. Targeted substitutes covered part of their scope — a purpose-built AXML decoder for the manifest properties MobSF would have reported, a manual exposure sweep and header inspection for part of a ZAP baseline, and pattern searches in place of Semgrep rules. The substitutes are narrower than the tools they replace, and no dynamic mobile analysis was performed at all.
  • The Google Maps key restriction status is undetermined. Billing is disabled on the Cloud project, so every API response returns the billing error before any restriction check is reported. Resolving this requires Google Cloud Console access.
  • The tested build predates current development. The deployed dashboard bundle is dated 19 October 2026 and does not include subsequent repository changes.
  • Availability, denial-of-service, business-logic abuse, and social engineering were out of scope.
  • A clean result is not proof of security. Eight issues were found; an absence of Critical findings reflects the tests performed, not the absence of Critical vulnerabilities.
  • One finding in this report was corrected after initial analysis (see §2.3 and §3.4). Readers should assume the same class of error is possible elsewhere in findings derived from pattern matching rather than structural parsing.

5.4 Conclusion

SafeSpace's backend authorization architecture is its clearest strength, and the evidence for that is specific rather than impressionistic: the anon role is denied at the grant layer on all 33 sensitive tables before RLS is consulted; the service-role key appears nowhere in either shipped client; all seven Edge Functions validate tokens server-side and enforce role allowlists; deletion of case, evidence, SOS, and audit records is impossible for every client role; and three tables are deliberately configured deny-all. These are design decisions that required deliberate effort, and they held under live testing.

The weaknesses cluster in deployment configuration rather than application logic. The absence of clickjacking protection on a dashboard managing survivor case records, an unrestricted-status Maps key, and a shipped artifact requesting microphone and screen-overlay permissions it does not appear to use are all gaps of configuration rather than code. They are correspondingly inexpensive to fix, and the first of them should be fixed promptly.

The honest summary is that this assessment verified the outer perimeter thoroughly and the interior not at all. For a system holding abuse survivors' identities, locations, and testimony, the interior is where the consequential risk lives, and the staging environment and authenticated testing described in section 5.2 should be treated as required follow-up rather than optional enhancement.
